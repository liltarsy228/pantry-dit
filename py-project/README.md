# Корпоративный учёт IT-активов

Внутренний Django-сервис для учёта компьютерной, серверной, сетевой техники, периферии и комплектующих. Приложение ведёт инвентарные номера, идентификаторы, характеристики, статусы и местоположения с историей изменений.

## Возможности

- Вход и операции управления доступны только активным пользователям Django с `is_staff=True`.
- Django Admin для наполнения справочников: разделов, типов, производителей, моделей, статусов, локаций, характеристик и видов идентификаторов.
- Список оборудования с поиском по идентификатору, модели и производителю, фильтрами по разделу, статусу и местоположению.
- Карточка оборудования с текущим состоянием, идентификаторами, характеристиками и историей статусов и перемещений.
- Добавление оборудования с безопасной атомарной выдачей номера вида `pc-000001`.
- Отдельные операции изменения статуса и перемещения, закрывающие предыдущий временной интервал.
- Редактирование модели, даты поступления, стоимости и примечания. Списанное оборудование остаётся в базе, но обычное редактирование запрещено.
- Валидация уникальности идентификаторов и допустимости характеристик для типа оборудования.

Текущие статус и местоположение не дублируются в `Equipment`: они определяются открытыми историческими записями с `valid_to IS NULL`.

## Требования

- Python 3.12 или новее.
- PostgreSQL и клиент `psql`.
- Unix-совместимая среда для Gunicorn (Linux/WSL/macOS). Для Windows без WSL используйте Django dev-сервер.

## Установка и настройка

### 1. Создайте PostgreSQL-пользователя и базу

Откройте консоль PostgreSQL от имени администратора:

```bash
sudo -u postgres psql
```

Выполните команды, заменив пароль:

```sql
CREATE ROLE it_assets LOGIN PASSWORD 'надёжный_пароль';
CREATE DATABASE it_assets OWNER it_assets;
ALTER ROLE it_assets CREATEDB;
\q
```

`CREATEDB` нужен только для автоматического создания временной тестовой базы командой `python manage.py test`.

### 2. Создайте виртуальное окружение и установите зависимости

Если проект находится на смонтированном диске Windows (`/mnt/c/...`) и создание `.venv` завершается ошибкой прав доступа, создайте окружение в файловой системе WSL:

```bash
python3 -m venv ~/.venvs/it-assets
source ~/.venvs/it-assets/bin/activate
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
```

### 3. Настройте `.env`

Скопируйте пример:

```bash
cp .env.example .env
```

Заполните `.env`:

```env
DJANGO_SECRET_KEY=длинный_случайный_секрет
DJANGO_DEBUG=true
DJANGO_ALLOWED_HOSTS=localhost,127.0.0.1

POSTGRES_DB=it_assets
POSTGRES_USER=it_assets
POSTGRES_PASSWORD=надёжный_пароль
POSTGRES_HOST=127.0.0.1
POSTGRES_PORT=5432
```

Сгенерировать секрет можно так:

```bash
python3 -c "import secrets; print(secrets.token_urlsafe(50))"
```

Django загружает `.env` автоматически, поэтому перед командами `manage.py` не нужно выполнять `export` переменных. Реальный `.env` игнорируется Git; в репозиторий добавляется только `.env.example`.

### 4. Примените миграции и создайте администратора

```bash
python manage.py migrate
python manage.py createsuperuser
```

Панель справочников доступна по адресу `http://127.0.0.1:8000/admin/`. До создания оборудования добавьте хотя бы локацию, тип, производителя и модель.

## Запуск в режиме разработки

```bash
python manage.py runserver
```

Откройте `http://127.0.0.1:8000/`. Войдите под суперпользователем или другим активным пользователем с `is_staff=True`.

## Тесты

Полный набор тестов рассчитан на PostgreSQL:

```bash
python manage.py test
```

Тест-раннер создаёт отдельную базу данных с префиксом `test_` и затем удаляет её. Для него PostgreSQL-пользователь должен иметь право `CREATEDB`.

Среди прочего тестируются:

- параллельная выдача уникальных инвентарных номеров и состояние `InventorySequence`;
- уникальность идентификаторов на уровне форм и БД;
- допустимость характеристик для типа оборудования;
- закрытие старых и создание единственных открытых записей статуса и местоположения;
- запрет операций управления для не-`is_staff` пользователей;
- редактирование карточки и защита списанного оборудования.

Параллельный тест использует блокировки PostgreSQL. SQLite не поддерживает эквивалентный механизм `SELECT FOR UPDATE`, поэтому он не является заменой PostgreSQL для этой проверки.

## Запуск через Gunicorn

Gunicorn запускает WSGI-приложение из `config.wsgi`. После установки зависимостей используйте:

```bash
gunicorn --bind 127.0.0.1:8000 config.wsgi:application
```

Для локальной проверки нескольких worker-процессов:

```bash
gunicorn --bind 127.0.0.1:8000 --workers 2 config.wsgi:application
```

Gunicorn читает те же настройки `.env`, что и `manage.py`. Nginx, HTTPS, production-логирование, `collectstatic`-развёртывание и systemd-сервис сознательно не входят в текущий этап.

### Статические файлы и пути

Перед подключением Nginx задайте в `config/settings.py` путь для собранной статики:

```python
STATIC_ROOT = Path("/var/www/it-assets/static")
```

Затем выполните `python manage.py collectstatic`. Nginx должен иметь право читать эту папку и отдавать её по `/static/`. В WSL не рекомендуется указывать `STATIC_ROOT` внутри проекта на `/mnt/c/...` (в частности, в OneDrive): Windows-раздел может запрещать Django менять права файлов. Для локальной WSL-проверки используйте папку в Linux-файловой системе, например `/home/<пользователь>/it-assets-static`; на сервере — общую читаемую Nginx директорию наподобие `/var/www/it-assets/static`.

## Основные маршруты

| URL | Назначение |
| --- | --- |
| `/` | Перенаправляет на список оборудования |
| `/login/` | Вход |
| `/admin/` | Панель Django Admin и справочники |
| `/equipment/` | Список, поиск и фильтры |
| `/equipment/add/` | Добавление оборудования |
| `/equipment/<id>/` | Карточка и история |
| `/equipment/<id>/edit/` | Обычное редактирование карточки |
| `/equipment/<id>/status/` | Изменение статуса |
| `/equipment/<id>/location/` | Перемещение |
| `/equipment/<id>/identifiers/add/` | Добавление идентификатора |
| `/equipment/<id>/characteristics/add/` | Добавление характеристики |

## Структура

- `config/` — настройки Django, маршруты и WSGI-точка входа.
- `apps/inventory/models.py` — нормализованная модель данных и ограничения целостности.
- `apps/inventory/services.py` — атомарные операции создания, смены статуса, перемещения и редактирования.
- `apps/inventory/forms.py` — формы и пользовательская валидация.
- `apps/inventory/views.py` — staff-only интерфейс.
- `apps/inventory/tests.py` — автоматические бизнес-тесты.
- `docs/database.md` — описание схемы БД и нормализации.
